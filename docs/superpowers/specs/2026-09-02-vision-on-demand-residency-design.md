# On-demand vision residency on the v0.6.2 resource model

Status: approved design, implementation in two stages on `feat/vision-on-demand-residency`
(base `release/v0.6.2-rtx3090`). Supersedes PR #8 (`feat/vision-vram-overlay`, base v0.6.0),
which predates the upstream Program-owned resource model and conflicts with it in 77 files.

## 1. Problem

`--vision` on `release/v0.6.2-rtx3090` keeps three things resident for the process lifetime:

| Reservation | Where it is planned | Size on Qwen3.8-27B |
|---|---|---|
| Vision tower + merger weights | single weight arena, `artifact::materialize` (`src/artifact/materializer.cpp:106`) | 282 MiB |
| Vision encode workspace, sized for `min(max_context, kMaximumVisionItemTokens=16384)` merged tokens | `build_workspace_plan`, `layouts_impl.h:581-586`, folded as `capacity = max(general, vision.capacity_bytes)` | encode peak ≈ 826 MiB minus `general_capacity` |
| Vision output handoff `[out_hidden=5120, max_merged]` BF16 | `VisionWorkspacePlan::handoff_*`, `vision_context_impl.h:216-240` | 160 MiB |

Measured on a 24 GiB RTX 3090 (`--kv-capacity` bisected, MTP3, C1): `--vision` costs
24,576 int8 tokens (155,648 → 131,072) and 40,960 rk8v4 tokens (212,992 → 172,032). Upstream's
`fc5c4834` (reclaim transient workspace) is already in this base; the residual is the table above.

Goal (owner decision): with `--vision` the engine boots the same KV capacity as without it, the
per-image cost stays in the PR #8 envelope (≈0.4 s per 1080p image, bit-identical embeddings), and
text generation performance is unchanged. Where more can be moved to the host without losing
performance, do it; the honest answer is that every other device resident (text weights, lm_head,
embedding, MTP head, KV, workspace, state slots) is on the per-step path, so the mechanism is built
as a generic on-demand weight group and vision is its only client.

## 2. Facts about the base that shape the design

1. **Serial executor.** `EngineCore` has one worker thread and one execution stream; each boundary
   runs exactly one GPU unit, prefill *or* decode (`engine_core.h:1756-1856`). Vision encode runs
   inside the prefill chunk unit (`prefill_multimodal_chunk`, `text_prefill_impl.h:74-92`), so in
   resident mode every other lane already waits for each image encode. Prefill is chunked and a
   chunk is capped at an item boundary (`VisionPrefillSession::prepare_chunk`), so the blocking
   granularity is one image, not one prompt.
2. **One weight arena, one workspace, decode graphs bake workspace addresses.** Text decode is
   captured into CUDA graphs rooted at `workspace_storage.base()` (`program_impl.h:9493-9812`,
   `graph_impl.h:20-24`); the general prefix `[0, general_capacity)` must never move. Vision is never
   captured and no captured graph references vision weights.
3. **Static KV capacity.** `--kv-capacity auto` resolves once at startup from
   `free_after_weights − 1 GiB headroom` against an affine curve whose device reservation is
   `persistent + workspace.capacity + graph_allowance` (`kv_capacity.cpp:77-141`,
   `layouts_impl.h:737-739`), checked twice (`registry.cpp:124-127`, `layouts_impl.h:812-815`).
   Bytes not reserved at plan time become KV pages; bytes freed at run time do not.
4. **Countable resource vector.** `PhysicalDeviceResources{active_lanes, state_slots,
   main_kv_pages, backend_kv_pages}` (`program.h:114-138`) has no device-byte axis; eviction is
   decided by `ResourceManager` + `MaterializationPlanner` over `PressureDecision`s generated by the
   Program; at most one global resource transaction is open at a time
   (`MaterializationTransaction`, `program.h:854-856`).
5. **Paged KV geometry.** A page holds 64 tokens (`kPagedKVPageSize`); the main text pool has one
   plane per (full-attention layer, K/V) — 16 layers × 2 = 32 planes on the 27B — laid out
   page-major inside each plane, so a run of consecutive physical pages is contiguous *within* a
   plane. Logical pages reach physical pages through block tables (`KVAddressSpaceStore`), so a
   physical page can be relocated by copy + table update without touching kernels or graphs.
6. **No VMM anywhere today**; `DeviceArena`/`DeviceBuffer` are plain `cudaMalloc`.

## 3. Design overview

Two currencies, one lease API, two stages.

```
                      VisionResidencyBroker (Program-owned, one open window at a time)
                              │
        ┌─────────────────────┴──────────────────────┐
   Tier 1 (stage 2)                              Tier 2 (stage 1)
   free KV page runs, VMM-remapped into          evict-ranked read-only weight tail
   the vision VA; decode of other lanes          (lm_head → embedding → draft → MTP),
   continues, encode is asynchronous             VMM-remapped into the vision VA;
                                                 exclusive, synchronous inside the unit
```

Policy: a window asks the broker for `window_bytes`. If enough free KV runs exist (tier 1), the
lease is taken from them and the encode runs asynchronously on a dedicated stream while the worker
keeps scheduling other lanes. Otherwise (tier 2) the broker evicts the weight tail, the encode runs
synchronously inside the prefill unit, and the tail is restored before the unit ends. Tier 2 is
always available (the tail is ≈3.35 GiB, the largest window is ≈1.1 GiB), so a vision request never
fails for lack of memory once admitted.

Stage 1 ships tier 2 plus everything that is currency-independent and already returns the full KV
capacity. Stage 2 adds tier 1 on top; tier 2 stays as its fallback.

## 4. Stage 1: on-demand vision group with the weight-tail currency

### 4.1 Options and startup features

- `include/ninfer/types.h`: `enum class VisionResidency { Resident, Overlay }`;
  `EngineOptions::vision_residency` (default `Resident`); `EngineOptions::vision_max_merged_tokens`
  (default `kMaximumVisionItemTokens` = 16384, accepted range `[64, 16384]`).
- `--vision-residency resident|overlay` and `--vision-max-merged N` in `serve_options.cpp` and
  `apps/cli/options.cpp`; `overlay` requires `--vision`; `--spec dflash` stays incompatible with
  `--vision`. Names are kept from PR #8 because production already runs
  `--vision-residency overlay --vision-max-merged 12288`.
- `qwen3_6::StartupFeatures` gains `VisionResidency vision_residency` (still compared with
  `operator==` as the frozen startup contract). `vision` stays the "vision enabled" bit.

### 4.2 Artifact layer: placements and the evict-ranked tail

`src/artifact/binder.h`, `binder.cpp`, `materializer.h`, `materializer.cpp`, `typed_binding.*`:

- `TensorPlacement` gains `HostPinned`: the object gets no device offset; its payload lands in one
  contiguous pinned block laid out with the same alignment rules as the device arena
  (`MaterializationPlan::pinned_capacity_bytes`, `pinned_objects`). `MaterializedArtifact::
  storage_data(handle)` returns the device pointer when present, else the pinned pointer;
  `is_host_pinned(handle)` and `pinned_block()` expose the block for the streaming layout.
- `Binder::materialize_on_device(handle, evict_rank = 0)`: ranked objects are withheld from the
  normal bump and packed by ascending rank after the unranked objects, starting at
  `MaterializationPlan::evictable_tail_offset` (aligned to the pool chunk). Higher rank = closer to
  the arena end = evicted first. Ranks (27B and 35B-A3B): MTP 400, draft head 500, token
  embedding 600, lm_head 700. Decoder blocks are unranked.
- The materializer places every object at `placement.offset` from the plan instead of replaying a
  bump allocation, so the tail boundary needs no synthetic alignment on the first tail tensor
  (PR #8 weak point 6 removed). Direct-I/O staging slots keep their explicit 4096-byte alignment.
- `materialize(reader, plan, device, progress, backing_pool)`: when a pool is given, the device
  arena is a non-owning view over the pool's home mapping; otherwise unchanged.

### 4.3 `core/evictable_weight_pool` (VMM)

`src/core/evictable_weight_pool.{h,cu}`, ported from PR #8 with these contract changes:

- Construction: home VA = `align_up(arena_bytes, kChunkBytes=16 MiB)`; physical pieces: unranked
  prefix in ≤1 GiB pieces, evictable tail in 16 MiB chunks; **overlay VA sized to
  `window_capacity_bytes`** (a constructor argument), not to the whole tail.
- `mirror`: pinned copy of only the last `window_capacity_bytes` of the tail, captured once after
  load (`capture_window_mirror`). PR #8 pinned the entire 3.35 GiB tail; this pins ≈1.1 GiB at
  most and only what a window can dirty.
- `Transaction evict(std::size_t bytes)`: synchronizes `stream` and `transfer_stream` itself (the
  quiesce is enforced, not documented), unmaps the minimal chunk suffix from home, maps the same
  handles into the overlay VA, returns the overlay base. Zero device allocations.
- `restore(stream)`: remaps home and re-uploads **only the dirtied chunk range** from the mirror
  (PR #8 uploaded from the first evicted chunk to the arena end), then synchronizes.
- `Transaction` is move-only RAII; its destructor calls `close()` which is `noexcept`: a restore
  failure is recorded as `poisoned()` and logged, never thrown from a destructor. The Program
  checks `poisoned()` after every window and fails the engine loudly (weights would be garbage).
- `supported(device)` probes `CU_DEVICE_ATTRIBUTE_VIRTUAL_ADDRESS_MANAGEMENT_SUPPORTED`; startup
  rejects `overlay` with a clear message when it is false.

### 4.4 Target load plan (27B and 35B-A3B)

- `plan_load`: in overlay mode the vision group (`bind_vision_backbone`, merger input, merger
  norm, `merger_fc2`) is placed `HostPinned`; text endpoints get evict ranks; `finish(kChunkBytes)`.
- `LoadPlan::vision_overlay` (`VisionOverlayLayout`): pinned block ranges of the prelude
  (patch/position embedding + bias), each of the 27 layers, and the merger group, computed from
  the plan's pinned offsets (explicit ranges; no contiguity heuristic — PR #8 weak point 7),
  `slot_bytes` = largest layer, `staging_bytes = prelude + merger + 2 × slot_bytes`.
- `VisionOverlayPlan` (per target, at plan time): `window_capacity_bytes =
  staging_bytes + encode_peak_bytes(vision_max_merged) + handoff_bytes(vision_max_merged)`,
  rounded up to `kChunkBytes`. Admission rejects any item whose window need exceeds it; fit-and-
  scale (4.8) makes that unreachable for well-formed media.
- `LoadedModelData::vision` in overlay mode is a host-side `VisionWeights` view used only as the
  rebase source for the streamed window view. It is wrapped in a `HostVisionWeights` type so the
  resident `VisionContext` constructor cannot be built over host pointers by mistake (PR #8 weak
  point 4).

### 4.5 Sequence plan: no resident vision reservations

`build_workspace_plan` (`layouts_impl.h`): in overlay mode `out.vision` still records
`max_merged_tokens`, `encode_peak_bytes`, `handoff_capacity_bytes` (the window needs them) but
`out.capacity == out.general_capacity`. The Program allocates `workspace_storage(general_capacity)`
and the decode graphs are unaffected. The capacity curve therefore matches the no-vision curve
except for the small prefill staging below, and `resolve_kv_capacity` returns the no-vision capacity.

Prefill staging: `TextPrefillRoots` gains `visual_embeddings` = BF16 `[hidden, scatter_tokens]`
allocated only when the plan is overlay (`scatter_tokens = min(prefill_chunk, vision_max_merged)`).
Cost: `5120 × prefill_chunk × 2` bytes = 10 MiB at the default 1024-token chunk, inside the
`text_prefill` envelope, which is rarely the maximum of the general capacity.

### 4.6 The window: `VisionOverlaySession`

`src/targets/qwen3_6/impl/runtime/vision_overlay.h` / `vision_overlay_impl.h` (new):

- Owned by `VisionPrefillSession` when the model is in overlay mode; constructed in
  `reserve_materialization` next to the existing session (`program_impl.h:4093-4101`) with no GPU
  work. Items behind the reuse boundary never appear in `plan.uses`, so a follow-up turn over the
  same image opens no window.
- `prepare_chunk` opens a window when a chunk reaches a *new* item (one window per item, not per
  request, so other lanes' decode units interleave between images):
  1. `broker.acquire(window_need(item))` → tier 2 in stage 1: `pool.evict(...)`.
  2. Slice the leased VA into `staging | handoff | encode workspace`.
  3. `VisionWeightStream` refills `slot[layer % 2]` one layer ahead on `transfer_stream`, event-
     fenced against the encode stream (PR #8's `+1` schedule); prelude and merger uploaded once
     per window.
  4. `VisionContext::encode` over the rebased window view writes the handoff inside the lease.
  5. D2H the handoff into the lane's slot of a pre-allocated pinned result pool
     (`max_concurrency × handoff_bytes(vision_max_merged)`, allocated at startup — no
     `cudaMallocHost` inside a window, PR #8 weak point 12).
  6. `broker.release()` → `pool.restore(stream)` and poison check.
- Per chunk, the session uploads only that chunk's visual columns from the pinned result into
  `roots.visual_embeddings` and returns `VisionChunk{length, control, embeddings, chunk_local=true}`.
  `TextContext::prefill_chunk` and `mtp_bridge_multimodal` use the column index relative to the
  chunk when `chunk_local` is set; resident mode keeps slicing the device handoff as today.
- The pinned result of an item is released with the item's media payload
  (`release_encoded_media_payloads`) and at `retire_handoff`.
- Telemetry: `VisionOverlayWindowStats{window_seconds, evict_seconds, restore_seconds,
  evicted_bytes, staged_bytes}` summed per request into `GenerationTimings::overlay_*`, printed in
  the serve request log line; `MemorySummary::vision_workspace` gains `residency`,
  `window_capacity_bytes`, `pinned_weight_bytes`, `mirror_bytes`. Window time is measured with CUDA
  events on the encode stream only (one clock, PR #8 weak point 11).

### 4.7 Exclusivity and safety

Tier 2 unmaps lm_head and friends, so nothing else may run on the device during a window. Stage 1
relies on two enforced facts, not conventions: the window is opened and closed inside one GPU unit
of the single worker, and `evict()` synchronizes both streams before remapping. The broker holds at
most one window and refuses a second `acquire` (logic error). If the engine ever grows a second
execution stream, the broker is the single place that must learn about it.

### 4.8 Media budget (fit-and-scale)

`--vision-max-merged N` is converted into smart-resize pixel ceilings at frontend construction
(`processor_options`), so oversized images and videos are downscaled to fit `N` merged tokens
instead of being rejected; this applies in both residency modes. The effective ceilings are logged
once at startup so the behaviour is visible (PR #8 weak point 9). Aggregate prompt vision tokens
stay bounded by `kMaximumPromptVisionTokens`.

## 5. Stage 2: free-KV-run currency and asynchronous encode

### 5.1 VMM-backed KV planes

The paged KV planes of the main text pool move out of the plain `persistent` arena into
`core/evictable_kv_pool`: each plane keeps its VA and tensor view (kernels and block tables are
unchanged), physical memory is created per *page run* (256 pages = 16,384 tokens) and mapped per
plane, so run `r` owns 32 pieces of 16 MiB (K) / 8 MiB (V) on the rk8v4 27B (≈384 MiB per run,
≈1 GiB per three runs). Block tables, state images, replay records and the MTP pool stay in
`persistent`.

### 5.2 Lease

`lease_runs(count)` picks the highest fully free runs, unmaps their pieces from all planes, and maps
them consecutively into the vision VA (overlay VA of the broker, shared with tier 2). `release()`
maps them back; free pages carry no content, so nothing is copied. The KV allocator hands out
physical pages lowest-first and the pressure planner's page choice prefers the highest runs as a
tie-breaker, so the top of the pool stays free unless the pool is genuinely full.

### 5.3 Accounting

A lease is an owner-less occupancy of `main_kv_pages` (256 per run) added to
`physical_occupancy()`; `admission_capacity()` and `materialization_deficit()` see it without new
axes; `advance_resource_revision()` runs on acquire and release so sealed `ResourcePlan`s stay
sound. The lease never triggers eviction of live pages: when fewer free runs exist than the window
needs, the broker falls back to tier 2 instead of asking the planner to displace anyone.

### 5.4 Asynchronous encode

In tier 1 the window does not run inside the prefill unit. `prepare_chunk` submits the encode on a
dedicated `vision_stream` (weights streamed on `transfer_stream`), records a completion event, and
the lane enters `WaitingForVision`; the scheduler skips that lane's prefill units until the event has
completed (polled at each boundary) and keeps running other lanes' decode and prefill units on
`device.stream`. On completion the handoff is D2H'd into the pinned result slot, the lease is
released, and the lane resumes with the per-chunk staging path of stage 1. Tier 2 windows keep the
synchronous stage 1 path.

### 5.5 Validation additions

- Text lane per-token latency while a 1080p image encodes at `--max-concurrency 2`: no stall
  ≥ 100 ms in tier 1; the stage 1 stall reappears when the pool is filled (tier 2 fallback forced by
  a long context) and the window still succeeds.
- KV capacity, TTFT, and parity numbers from 4.10 unchanged.
- `tests/test_evictable_kv_pool.cu`: run lease/release keeps plane addresses stable, leased runs
  are excluded from allocation, block-table reads through a leased run are impossible by
  construction (allocator test), remap under a captured decode-shaped graph.

## 6. Deliverables and process

- One branch, two milestones; each milestone is green on the pod before the next starts.
- A draft PR into `Don-Chad/ninfer-3090:release/v0.6.2-rtx3090` replacing #8, whose body carries the

## 7. Out of scope

- Windows builds (documented limitation, as in the merge PR).
- Offloading any per-step resident (lm_head, embedding, MTP head, KV, workspace, state slots).
- 35B-A3B validation on a 24 GiB card (the artifact does not fit); it gets code parity only.
- Concurrent prefill/decode execution beyond the tier 1 asynchronous vision encode.
